# Specify — CLAUDE.md（Cursor / Claude Code 向け）

このリポジトリは **Microsoft Agent Hackathon 2026 提出用** です。**完成度と Agentic AI らしさ**を最優先にする。

## プロダクト一文

**PRD から「決まっていない意思決定」を体系的に炙り出し、画面プレビューで体験できるようにするマルチエージェント。**

## 背景・先行事例への向き合い方

2026-04-30 に CADDi 山崎さん「Figmaを使わずStorybookでデザイン描いたら検討漏れが131件見つかった」という記事が公開された。Specify はこの実践を**先行事例として強くリスペクト**しつつ、AI Agent によって**誰でも・どんな組織でも実行可能にする**ことを目指す。

CADDi 実践の前提条件:
- デザインシステムが整備済み
- エンジニアの伴走がある
- Storybook を書く時間と環境がある

→ これらが揃わない組織でも、PRD を投げれば「決めるべき意思決定」が可視化される、というのが Specify の存在意義。

## デモで見せる体験（最低限）

1. PRD（テキスト or Notion URL）を入力する
2. **3 つのエージェントが並列で動く様子**が画面に出る
3. **「未定義の意思決定: 18件」**のように、決まっていないことが可視化される
4. 各論点に**優先度**と**決めるべき選択肢**が付く
5. 軽量プレビューで**各状態の画面を切り替えて確認**できる
6. 過去 PRD との矛盾も並列で検出する

### デモが成立する例（架空 SaaS「KintaiKit」）

新 PRD「ユーザー追加モーダル機能」を投入すると、次のような結果が出る:

> **🔴 必須の意思決定**
> - バリデーションタイミング: onChange / onBlur / onSubmit のどれ？
> - 30文字超の名前の表示: 折り返し / 省略 / 横スクロール？
> - 重複メールアドレス入力時の挙動
>
> **🟡 推奨の意思決定**
> - Loading 中の操作可否
> - 全角英数字の自動変換
>
> **🔴 過去 PRD との矛盾**
> - 2024 年 Q3 PRD で決定した「管理職のみ申請可」ルールと矛盾

最初は **意思決定リスト生成 1 機能のみ** でも可。プレビュー・過去 PRD 連携は段階的に追加。

## 画面は 3 つのみ

| 画面 | 役割 |
|------|------|
| **入力画面** | PRD のテキスト入力 or Notion URL 入力 |
| **分析中画面** | 3 エージェントが動いている様子をリアルタイム表示（agentic 感の核） |
| **結果画面** | 意思決定リスト + 軽量画面プレビュー + 過去 PRD 矛盾 |

ルーティング例: `/`（入力）、`/analyzing`、`/result` — 名前は実装で統一すればよい。

## 技術構成（固定）

- **フロント**: Next.js（App Router）+ TypeScript
- **バック**: Python（FastAPI または Azure Functions の Python ランタイム）
- **オーケストレーション**: **Microsoft Agent Framework 1.0**
- **エージェント基盤**: **Azure AI Foundry Agent Service**
- **モデル**: **Azure OpenAI**（GPT-4o-mini 中心、判断要所のみ GPT-4o）
- **ツール連携**: MCP（Model Context Protocol）経由で Notion / GitHub
- **実行基盤**: **Azure Functions** または **Azure Container Apps**
- **ホスティング（フロント）**: **Azure Static Web Apps**
- **データ**: **DB は使わない**

## エージェント設計（agentic 感を出す核）

```
[Planner Agent]
  PRD を読んで「何を分析すべきか」の計画を立てる
  例: "ユーザー追加モーダル機能。フォーム系の論点と、
       過去のフォーム関連 PRD との整合性をチェック"
       ↓
┌────────────────┬────────────────┬────────────────┐
│ Decision Agent │ Edge Case Agent│ Past PRD Agent │
│ 意思決定論点を │ 異常系・状態   │ 過去 PRD から  │
│ 体系的に列挙   │ パターン列挙   │ 関連事項取得   │
└────────────────┴────────────────┴────────────────┘
       ↓
[Reviewer Agent]
  3 つの結果を統合・優先度付け・重複排除
       ↓
出力:
  - 優先度付き意思決定リスト
  - 各状態の画面プレビュー（軽量プレビュー）
  - 過去 PRD との矛盾レポート
```

**重要**: ただの RAG に見えないように、Planner の判断・各エージェントの並列実行・Reviewer の統合判断を **UI 上で可視化する**。

## 主機能（優先度順）

### 1. 意思決定リスト生成（メイン）

PRD から「まだ決まっていないこと」を体系的にリストアップする。

**対象論点の例**:
- バリデーションタイミング（onChange / onBlur / onSubmit）
- Empty State の表示
- Loading 中の表示・操作可否
- エラー処理（フィールド単位 / 画面単位）
- 長文の表示方法（折り返し / 省略 / 横スクロール）
- 権限別の見え方
- モバイル表示
- 空配列の扱い
- デフォルトのソート順
- ページネーション仕様
- i18n ラベル定義
- アクセシビリティ（キーボード操作、スクリーンリーダー）

各項目には:
- 優先度（🔴必須 / 🟡推奨 / 🟢任意）
- 決めるべき選択肢（具体的な候補）
- 「なぜ決める必要があるか」の根拠

### 2. 軽量画面プレビュー（サブ）

各状態の画面を Next.js 上で軽量にプレビューする。

- Default / Empty / Loading / Error / LongText / Disabled などの状態を切り替えられる
- 「未定義」状態には ⚠️ マークを表示
- **本物の Storybook ランタイム統合はしない**（実装範囲外）

### 3. 過去 PRD 整合性チェック（サブ）

Notion から過去 PRD を参照して矛盾検出する。

- 関連する過去 PRD を検索
- 新 PRD との論理的矛盾を検出
- 該当する過去ページへのリンクを表示

## データフロー（MVP）

```
ユーザー入力（PRD テキスト or Notion URL）
  → Planner が計画を立てる
  → 並列で Decision / Edge Case / Past PRD Agent を実行
  → Reviewer が統合判断
  → 意思決定リスト + プレビュー + 過去 PRD 矛盾を返却
  → 画面に表示
```

## Azure 連携の置き場所

- **Azure OpenAI**: バックエンド（Python）からのみ呼ぶ。**ブラウザにキーを置かない**
- **環境変数**:
  - `AZURE_OPENAI_ENDPOINT`
  - `AZURE_OPENAI_API_KEY`
  - `AZURE_OPENAI_DEPLOYMENT_NAME`
  - `NOTION_API_KEY`
  - `GITHUB_TOKEN`（過去実装参照用、オプション）

## 禁止事項（守る）

- 大規模リファクタ
- 認証の追加（デモは 1 ユーザー前提）
- DB の追加
- **Figma 連携**（今回は使わないことが価値）
- **本物の Storybook ランタイム統合**（実装範囲外）
- **任意のデザインシステム読み込み**（実装範囲外）
- **実コード生成（.tsx 出力）**（実装範囲外）
- Slack 連携
- 修正案の自動生成
- 学習機能・履歴機能
- 複数ワークスペース対応
- 既存 UI の意図的な破壊
- 仕様の勝手な拡張
- **不要なライブラリ追加**

## デモデータについて（架空 SaaS「KintaiKit」）

## 重要な注意事項

### Python に不慣れ
本人は Python に不慣れ（フロントエンド・軽いツールレベル）。
コード生成時は以下に配慮:
- 型ヒント（type hints）を必ずつける
- なぜそう書くかをコメントで添える（特に async / await、デコレータ周り）
- venv または uv で仮想環境を作る前提
- 不慣れさを補う説明を、コード行数の 30〜50% 程度添える

### Microsoft Agent Framework 1.0 は新しい
2026 年 4 月 GA したばかり。Web の情報がまだ少ないため:
- 不明な API は推測で書かず、公式ドキュメントを参照する旨を明示する
- バージョン互換性に注意（古い Semantic Kernel のサンプルは流用しない）
