# Past PRD ドラフト + Notion セットアップ手順

**用途**: KintaiKit デモの Past PRD として Notion に投入する 4 件のドラフトと、Notion DB の準備手順。`backend/src/specify_backend/notion.py` は `domain="kintaikit"` Select プロパティで filter する想定なので、各ページに **必ず `domain = kintaikit` を設定** すること。

---

## 1. Notion DB セットアップ

### 1.1 既存 DB に `domain` プロパティを追加

`NOTION_PRD_DB_ID` 環境変数で指定している既存の DB を開いて:

1. データベースのオプション → **Properties** → **Add a property**
2. 名前: `domain`（lowercase 厳密、コード側と一致させること）
3. タイプ: **Select**
4. オプションに `kintaikit` を追加（将来 `ec` / `medical` を増やす想定）

### 1.2 既存ページに domain タグを付与

既存の Past PRD ページ（あれば）に `domain = kintaikit` を割り当てる。`domain` 未設定のページは filter で除外され、`backend` ログに「Notion から過去 PRD を 0 件取得（domain=kintaikit）」と出るので、その状態になっていないか確認。

### 1.3 動作確認（任意）

```bash
cd backend
uv run python -c "from specify_backend.notion import fetch_past_prds; r, f = fetch_past_prds(domain='kintaikit'); print(len(r), f)"
```

`<件数> None` が出れば OK。`0 None` だった場合は domain プロパティの値ミスマッチ、`0 notion_fetch_failed` だった場合は API キー or DB ID の設定漏れ。

---

## 2. 投入する Past PRD（4 件）

以下を Notion で新規ページとして 1 件ずつ作成。**Name プロパティに `## タイトル` の中身**、ページ本文に **「本文」セクション以下** をコピペ。`domain` プロパティに `kintaikit` を選択。`Topics` プロパティがあれば任意でタグを付ける（filter には使っていないので空でも可）。

### P1. 監査ログに関する運用原則

**Name**: `KintaiKit 運用原則: 監査ログ`
**domain**: `kintaikit`
**Topics**: `audit`, `security`

**本文**:

```markdown
## 背景

KintaiKit は労働基準法対応 / 内部統制を主な訴求点に据えており、顧客の社労士・経理から「誰がいつ何を変更したかを後から追えること」を強く期待されている。これに応えるための運用原則を本ドキュメントで定義する。

## 原則

- 全ての書き込み系操作（登録 / 編集 / 削除 / 承認 / 配信）を、改ざん不能な形で構造化して audit_log テーブルに記録する
- 記録項目: 実行ユーザー / 実行日時 / 操作種別 / 対象リソース ID / 変更前後の差分 / トランザクション ID
- 監査ログの削除・改変は禁止。物理削除しない（論理削除でログ自体には削除不可フラグ）
- 自動処理（バッチ・スケジューラ）も「システム」ユーザーで監査ログを残す
- アルゴリズム判断（シフト自動割当等）は、判断根拠（入力パラメータ / 出力結果）も合わせて記録

## 適用範囲

- 全ての管理者画面の操作
- 全ての自動配信・スケジューラ実行
- API 経由の全ての書き込みリクエスト
```

### P2. 個人情報取扱いポリシー

**Name**: `KintaiKit 個人情報取扱いポリシー`
**domain**: `kintaikit`
**Topics**: `privacy`, `compliance`

**本文**:

```markdown
## 背景

KintaiKit は氏名 / メールアドレス / 雇用形態 / 給与情報など、複数の個人情報を扱う。個人情報保護法 (APPI) および各社のコンプラ要件に対応するため、取扱いポリシーを統一する。

## ポリシー

- 個人情報の追加 / 変更 / 参照は audit_log に必ず記録する（P1 と整合）
- 監査ログの保持期間: 5 年（労働基準法 109 条準拠）
- 個人情報を含むレポート / エクスポートには、配信先 / 配信日時 / 配信内容のハッシュを記録
- 暗号化: 保管時 AES-256、転送時 TLS 1.2 以上
- ログ自体に氏名・メールアドレスを平文で含めない（ハッシュ化、または PII マスキング）

## 削除要求への対応

- 個人情報削除要求 (GDPR Article 17 相当) を受けても、監査ログは削除しない（法定保持期間中）
- ただし監査ログ内の PII はハッシュ化済みのため、個人特定性は維持されない
```

### P3. 承認フロー基本方針

**Name**: `KintaiKit 承認フロー基本方針`
**domain**: `kintaikit`
**Topics**: `approval`, `workflow`

**本文**:

```markdown
## 背景

権限の濫用 / 不正操作を防ぐため、特定の操作については事前承認を必要とする。承認なしで実行できる操作と区別を明確にする。

## 承認が必要な操作

- ユーザー追加 / 削除（管理者権限を持つ別ユーザーの承認）
- シフトの確定（手動・自動を問わず、店長権限ユーザーの承認）
- 月次レポートの配信先変更（経営層メールアドレスを含む変更）
- 給与・賞与計算に影響する勤怠データの一括修正

## 承認プロセス

- 承認リクエスト時: リクエスト者 / 対象 / 理由 を必須入力
- 承認時: 承認者 / 承認日時 / コメント を記録
- 却下時も同様に記録
- 承認・却下・取り消し操作はすべて audit_log（P1）に記録

## 例外

- 緊急時のオーバーライド権限はオーナーアカウントのみ。発動時は社内 Slack に自動通知。
```

### P4. 通知配信ガイドライン

**Name**: `KintaiKit 通知配信ガイドライン`
**domain**: `kintaikit`
**Topics**: `notification`, `reliability`

**本文**:

```markdown
## 背景

メール / Slack / アプリ内通知など複数チャネルでユーザーに情報を届けている。配信の信頼性 / 追跡性 / リトライ性を統一する。

## ガイドライン

- 重要通知（給与・承認依頼・コンプラ通知）はメール + Slack の二重配信
- 配信ログ: 配信先 / 配信日時 / 配信内容ハッシュ / 配信結果（success / soft_bounce / hard_bounce）を全件記録
- 失敗時のリトライ: soft_bounce は指数バックオフで最大 3 回、hard_bounce は即停止
- リトライ履歴も audit_log（P1）に記録
- 配信先の変更（追加・削除）は承認対象（P3 と整合）

## 月次・定期配信

- スケジューラから配信されるレポート系は、配信成功までを 1 トランザクションとして扱う
- 配信失敗時はオーナーアカウントに自動通知（Slack）
- 個人情報を含むレポートは P2 のポリシーに従う
```

## 3. 投入後の動作確認

1. `docker compose down && docker compose up -d` で backend を再起動
2. ブラウザで http://localhost:3002 を開く
3. KintaiKit a/b/c のいずれかのカードを選ぶ
4. 結果画面で **「過去 PRD との矛盾」** セクションに 1 件以上の矛盾が出ていれば OK
5. 出ない場合は backend ログを確認:
   ```bash
   docker compose logs backend | grep "Notion"
   ```
   `Notion から過去 PRD を 0 件取得（domain=kintaikit）` → domain タグの設定漏れ
   `Notion 取得失敗` → API キー / DB ID の設定漏れ

## 4. 期待される矛盾検出パターン

| Demo PRD | Past PRD と矛盾しやすい論点 |
|---|---|
| a. ユーザー追加 | P1（audit 記録）, P2（個人情報ログ）, P3（承認フロー） |
| b. シフト自動割当 | P1（アルゴリズム判断ログ）, P3（シフト確定承認） |
| c. 月次レポート | P1（配信ログ）, P2（個人情報含む配信）, P4（配信失敗時リトライ） |

3 機能とも複数の Past PRD に刺さる構造なので、必ず 2-3 件の矛盾が検出されるはず。
